Talking to data directly vs. through code execution

Six retail questions, five SharePoint lists, the same answers every time — tried three ways. Direct hands the whole list to the model. Microsoft Graph asks the server to filter first. Code execution runs a small script and sends back only the answer. The thing we're counting is tokens: how much text the model has to read. Less is cheaper and faster. Graph only helps when the question is a simple "find these rows" lookup.

Three ways to get the same answer

Direct access

The tool hands over the whole list.

  • Model asks for the Sales list
  • All 4,000 rows come back
  • The model has to read every one
  • Then it works out the answer itself
# the model reads all of this
[{"OrderLineID":90000,
  "StoreID":1004,"Qty":3,
  "LineRevenue":146.7, ...},
 ... ×4000 rows ...]

Microsoft Graph

The server filters first — if the filter is simple.

  • Model says "only store 1004, March"
  • Server can match one column to one value
  • It can't add up or combine lists
  • So harder questions still send everything
# works for a simple lookup
GET /lists/Sales/items
 ?$filter=StoreID eq 1004
   and Month eq '2025-03'
# → 16 rows. need a total? all 4,000

Code execution

A small script does the work, sends back the answer.

  • Model reads a short list of what's available
  • Writes a few lines of code
  • The code runs where the data lives
  • Only the final answer comes back
# the model only reads the answer
rev = defaultdict(float)
for s in sp.sales():
    rev[s["ProductID"]] += \
        s["LineRevenue"]
# → "Black Sweater: $47,428"

Why Graph couldn't help

Graph is good at one thing: "give me the rows where this column equals this value." That's it. The moment a question needs more, Graph gives up and sends the whole list — so the model ends up reading just as much as direct access. Here are the four things it can't do, and the question each one broke on.

It can't add things up. Questions like "total revenue by region" (Q3) or "top 5 products by sales" (Q1) need every sale added together. Graph has no way to total numbers on the server, so it sends all 4,000 sales rows and the model adds them up itself. No saving.
It can't join two lists. "Revenue by region" needs Sales (which has store IDs) matched with Stores (which has the region). Graph can't connect two lists, so both come over whole and the matching happens on the model's side.
It can't compare two columns in the same row. "Which items are below their reorder point" (Q2) means checking OnHand < ReorderPoint — one column against another. Graph can only compare a column to a fixed value, so it can't do this at all and ships the entire Inventory list.
It chokes on big lists. SharePoint refuses to filter a list past 5,000 items unless the column was specially indexed ahead of time. Real sales tables are far bigger than that, so the simple filter that worked in this demo would often just fail in production.
The one time it worked (Q6): "list store 1004's March sales" is a plain lookup — one column equals one value, no adding, no joining. Graph handled it on the server and sent back 16 rows instead of 4,000. That's a 99.6% cut, about as good as code execution.
Bottom line. Use Graph for simple "find these rows" questions — it's easy and it works. For anything that totals, combines, or compares (the questions that actually cost a lot), Graph is no better than handing over the whole list. Code execution wins there because the adding, joining, and comparing all happen next to the data, and only the short answer comes back. The trade-off: you need a place to run the code, and the model has to write it correctly.

Tested against a live SharePoint tenant

Everything above uses generated data. To check it against reality, I pointed the same three approaches at a real company SharePoint over Microsoft Graph: a retail workforce dataset (stores, employees, shifts, scorecards, incentives) with 16 to 240 rows per file. Smaller data, so a smaller gap, but the shape held and the Graph behaviour matched the theory exactly.

Code execution cut the reading by 97%, on every question. Lower than the 99.8% on the generated data, and that's the point: these real tables have 16 to 240 rows, not thousands, so there's less to save. The mechanism is the same; the data is just smaller.
Graph split exactly along the line the theory predicted. It helped on the simple-shaped questions (filter a column, or take the top 5): 97% off the single-store lookup, 60 to 67% off the others. It did nothing, 0%, on the two questions that total and combine across files (hours by district, KPIs by district). Same story as the generated data, now on a live tenant.
*The honest asterisk. That Graph column is the best case, and it assumes the data lives in SharePoint Lists. On this tenant it doesn't: it's Excel files in a document library. Graph can read those files but can't hand back only the matching rows the way it can for a List, so in reality Graph here would tie Direct on all six. A lot of "SharePoint data" in the wild is Excel files, which quietly removes even the 50% Graph looked like it was winning.
